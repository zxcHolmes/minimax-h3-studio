# CLAUDE.md

## Repository language

Use English as the primary language for committed documentation, code identifiers, comments and user-facing UI text. Keep other languages only where the content requires them, such as native model labels, multilingual test fixtures, prompts or quoted source material. Conversation with the user may remain in their preferred language.

## Overview

MiniMax-H3 Studio: a MiniMax-H3 video generation service that **does not need the ComfyUI UI**. It is deployed to a single GPU machine and used from a browser.

- `comfy_launcher/`: headless launcher. Uses ComfyUI as a Python library and calls the nodes directly in the order of the official workflow, so it reuses ComfyUI's quantized checkpoints (int8 DiT, nvfp4 text encoder) and DynamicVRAM memory management. Output is **pixel-identical** to the official ComfyUI workflow (PSNR inf).
- `server/`: resident HTTP server. Weights load once, one job runs at a time, with a job queue and a sqlite record.
- `web/`: Vue 3 frontend with vertical task/model navigation: text to video, image to video (first frame / first + last frame), reference images and videos (Ref2VA), picture generation/editing (MOSS-Image, 4-step FLUX.2 Klein 4B, 8-step Qwen Image 2.1 Turbo; modes t2i/i2i) and music generation (MiniMax Music 3, mode t2m). Finished videos can be upscaled with FlashVSR v1.1 or SeedVR2 (mode upscale).
- `deploy.sh`: one-command deploy to the GPU machine; also downloads models remotely (`./deploy.sh models`).
- `scripts/prepare_models.py`: downloads every model the server uses (base models, text encoders, VAEs, LoRAs, MOSS-Image, MiniMax Music 3, SeedVR2, FlashVSR) into `$H3_COMFYUI/models`.

Deployment settings come from environment variables. Locally they live in `.env` (git-ignored); `.env.example` is the documented template. When adding a setting, update both `.env.example` and the configuration table in the README.

## Environment

- The GPU machine needs a ComfyUI checkout with MiniMax-H3 support (developed against 0.42). The server and launcher reuse ComfyUI's Python environment (conda or venv).
- The timings in the tables were measured on an RTX 4090 24GB with 125GB RAM and torch cu128. comfy_kitchen 0.2.39 is built from source for CUDA 12.8 / sm_89 on the GPU box (the cu13 wheel's CUDA ops do not load there), Stock ComfyUI's `comfy/quant_ops.py` calls `ck.registry.disable("cuda")` whenever torch is older than cu130, which left that build unused. The GPU box's ComfyUI carries a local patch (original in `comfy/quant_ops.py.orig`) that only disables the CUDA backend when its ops fail to load, so the server now runs with both the CUDA and the triton backends (startup log: `backend cuda: ... 'disabled': False`). Measured: a 12.3 s 544p larryvrh shot went from 108 s to 90 s. Re-apply the patch after updating ComfyUI (`git pull` may conflict with it). The full rebuild (cu128, sm_89, build script in `~/build/build_kitchen.sh` on the GPU box), install, patch and verification steps are in the README section "comfy_kitchen on PyTorch older than cu130". The `int8_tensorwise` + convrot checkpoints run their linear layers through `comfy_kitchen.int8_linear` (row-wise dynamic activation quantization + int8 matmul); `--enable-triton-backend` is still needed, because without kitchen's accelerated backends int8 matmul falls back to eager (the flag alone gave ~2× before the patch).
- When killing processes over ssh, use the bracket form `pkill -f "[m]ain.py ..."`, otherwise the pattern matches and kills the ssh session itself.

## Models and LoRAs (measured findings)

Shared components (under `$H3_COMFYUI/models/`):

| Component | File |
|---|---|
| FL2VA base (text / image / first + last frame) | `minimax_h3_fl2va_pruned_int8_convrot.safetensors` |
| Text encoder | `qwen3vl_32b_minimax_h3_nvfp4_awq.safetensors` |
| VAE | `minimax_h3_video_vae_int8_convrot` (as in every official H3 template) + `minimax_h3_audio_vae_fp32` |

Resolution (`RESOLUTIONS`: 544p = 960×544 pixel area, 768p = 1344×768 pixel area) and LoRA are independent choices. The base model follows the mode: reference jobs (ref2va family) run on the ref2va base (FastH3 OmniRef or the official ref2va base with the Pika LoRA), everything else uses fl2va. LoRAs are defined in `LORAS` in `server/model_catalog.py`; the recommended default per mode and resolution is in `DEFAULT_LORAS`:

| LoRA key | Base | File | Steps | Shift | Resolutions | 5 s clip |
|---|---|---|---|---|---|---|
| `larryvrh-v4-sparse` (default) | fl2va | `minimax_h3_turbo_v4_step600_ema` + Sol-Attn | 4 | 12/3 | 544p / 768p | 768p ~39s |
| `larryvrh-v4` | fl2va | `minimax_h3_turbo_v4_step600_ema` | 4 | 12/3 | 544p / 768p | ~31s / ~67s |

The lightx2v fl2v LoRAs (8-step v1.0 at 544p, 4-step v1.3 at 768p) were removed on 2026-10-31 at the user's request; their ids remain only in `LEGACY_PRESETS` for old jobs, which display the models stored in `result.models`. `larryvrh-v4-sparse` uses the same Sol-Attn settings as Pika's all-sparse choice (sampling 49 → 27 s for 5 s at 768p, comparable quality; Sol-Attn works with the larryvrh turbo sampler).

FastH3 (FastVideo's distilled 8-step bases) is a second model group (`GROUPS` in `model_catalog.py`). Its `LORAS` entries have `group: "fasth3"`, their own `unet` (+ `unet_source`), `file: None`, `loader: "none"`, a `sampler` and `vsa` settings:

| Key | Family | Base file | Sampler | Shift | VSA keep / start |
|---|---|---|---|---|---|
| `fasth3-v2` | fl2va | `fastvideo_fasth3_8step_v2_pruned_int8_convrot` | res_multistep | 10/3 | 10 / 0.2 |
| `fasth3-omniref` (reference default) | ref2va | `fasth3_omniref_8step_pruned_int8_convrot` | euler | 12/3 | 10 / 0 |

VSA needs comfy kitchen attention; on the GPU box comfy_kitchen 0.2.39 was rebuilt for CUDA 12.8 (sm_89), because the cu13 wheel crashes on driver 570. With the kitchen CUDA backend enabled (see Environment) a 5 s FastH3 clip takes ~39 s / ~71 s (V2, 544p / 768p) and ~41 s / ~67 s (OmniRef): faster than the old lightx2v 8-step LoRA, slower than the 4-step ones at 544p, about the same at 768p. The H3 + ref2v LoRA route (ref2va base + lightx2v `ref2v_turbo_4step` v0.1 / v1.0) was removed on 2026-10-23: on a fast sword-dance prompt it smeared moving sleeves and blades into comb-like streaks that read as dropped frames, at any sampler (euler / res_multistep) and still at 6–8 steps or strength 0.7, while OmniRef stayed clean at the same seed. The output was a true 24 fps / 260 frames; the stutter came from the per-frame smear. The 5 s timings in these tables were measured on 2026-10-22 after the kitchen patch (before it they were 17–48% slower).

Pika H3 Flex is the third group (`group: "pika"`): Pika's Comfy-format BF16 LoRAs (`Pika-Labs/Pika-H3-Flex`, file in the repo's `comfy/loras/`, hence `source_path`; `sha256` is verified by `prepare_models.py`, group `pika`) on the official int8 bases, `pika-flex-fl2va` on fl2va and `pika-flex-ref2va` on `minimax_h3_ref2va_pruned_int8_convrot` (back in `UNETS`). Settings from Comfy-Org's `video_pika_h3_flex_{t2v,fl2va,ref2va}` templates: sampler `lcm` (fresh noise per step) and `sigmas` = `PIKA_SIGMAS` (knots 1000/750/500/250/100/40/0 already shifted by 12); `_lora_model()` uses fixed `sigmas` instead of BasicScheduler when an entry has them. The templates have no SigmaShift node because ComfyUI's H3 default is 12/3, the same as our explicit SigmaShift. `fixed: True`: generic 6-step sampling is not Pika's contract. Measured on 2026-10-31: t2v 5 s 768p ~81 s (sampling 69 s); r2v 10.8 s 544p with one reference + guide audio ~95 s (sampling 79 s). On the sword-dance prompt that broke the lightx2v ref2v LoRAs, Pika ref2va kept sleeves and blade free of comb streaks and preserved the subject. `pika-flex-*-sparse-all` (the Pika default: the frontend recommends a group's first choice, so each family lists all-sparse, `-sparse`, dense) and `pika-flex-*-sparse` are the same LoRAs with `sol: {tau 1.3, start 0 / 0.2}`: the engine adds `BlockSparseAttention` with method `sol-attn` (training-free) instead of `vsa`, since VSA needs FastH3's learned `to_gate_compress` branch; at shift 12, start 0.2 leaves only the first step dense. Sampling dense / dense 1st step / all sparse: 69 / 38 / 34 s (t2v 768p 5 s) and 79 / 43 / 39 s (the r2v shot); the user judged all-sparse as good as the others; `prepare_models.py` lists each file once, since these entries share the LoRA.

Adding a LoRA only takes one entry in `LORAS` (with `source` set to its HF repo): the frontend picks it up through `/api/presets` and `prepare_models.py` downloads it. The base models, text encoder and VAEs all come from `Comfy-Org/MiniMax-H3`.

- Sampling uses the simple scheduler + BasicGuider (no CFG). The sampler is euler, except larryvrh, which uses its own turbo sampler.
- The shift must match the LoRA.
- The flags `--enable-triton-backend --use-sage-attention` make generation about 2× faster with no visible quality loss (on by default in the server). The w4a8 base is slower than int8.
- The larryvrh LoRA (`minimax_h3_turbo_v4_step600_ema`) needs its own nodes `MiniMaxH3TurboLoRA` + `MiniMaxH3TurboSampler` and shift 12. Its entry has `loader: "larryvrh"`, which makes the engine load those nodes from `custom_nodes/ComfyUI-MiniMax-H3-Turbo`. It loses subject identity in reference mode, so it is offered for fl2va only.
- Frame counts snap to the 17k+5 grid at 24 fps, e.g. 5 seconds is 124 frames.
- Image-to-video prompts need keyframe tags: `<Picture 1>` refers to the first frame and `<Picture 2>` to the last frame. The server adds them with `with_keyframe_prefix` when missing.
- Reference-mode prompts follow the official ref2va layout: subject_definitions / summary / retention_analysis / detailed_description / overall_soundscape / non_diegetic_music. The frontend assembles these sections from the reference images and their subject descriptions.

## Key files

- `comfy_launcher/run_h3.py`: headless launcher for single runs or batches via `--jobs-json`.
  - `bootstrap_comfy()` replicates the process-level setup of ComfyUI's `main.py`: argument parsing, cuda_malloc, `comfy_aimdo.control.init`, `init_devices`, and setting `CoreModelPatcher` to `ModelPatcherDynamic`. Without this DynamicVRAM step it runs out of memory.
  - Nodes are always called with keyword arguments, because ComfyUI reorders node signature parameters between releases.
  - `--lora-loader larryvrh` loads larryvrh's custom nodes. Arguments after `--` are passed through to ComfyUI.
- `comfy_launcher/bench.sh`: wraps run_h3.py, records peak VRAM with nvidia-smi and uses `flock gpu.lock` to run tests one at a time.
- `comfy_launcher/prompts_*.json`: test prompts.
- `scripts/split_book.py`: splits an epub (OPF spine order) or txt (UTF-8 / GB18030) into one text file per chapter plus `chapters.json`, for `doc/novel-adaptation-workflow.md`. Standard library only, run with `python3 -I`.
- `scripts/prepare_models.py`: standard library only, runs with any python3. The file list is built from `UNETS`, `CLIP`, the VAE constants, the `MOSS_*` and `MUSIC_*` constants and `LORAS` in `model_catalog.py`; existing files are skipped, `.part` files allow resuming, and `HF_ENDPOINT` selects a mirror. ComfyUI itself and the larryvrh custom node are cloned by the user, not by this script.
- `server/model_catalog.py`: standard-library-only model registry, LoRAs, inference defaults, prompt/frame/size helpers; both HTTP presets and model downloads read this module.
- `server/h3_engine.py`: resident runtime; owns bootstrap, caches, memory management and cancellation, and delegates inference to `server/pipelines/{video,picture,music,seedvr2,flashvsr,pixal}.py`. Shared image/audio/video IO is in `pipelines/media.py`. Keep GPU imports lazy, after bootstrap.
  - The text encoder and VAEs stay loaded. Only one base DiT is resident at a time (H3 fl2va / ref2va or a FastH3 base, see `unet_file()`); `_use_base()` unloads the old base before loading the new one. Because DynamicVRAM streams weights from mmap, a switch takes under a second.
  - Each model choice is a ModelPatcher clone of the resident base carrying its own LoRA (if any), SigmaShift, sampler and attention patches. It is created on first use and cached until the base switches, so switching LoRAs on the same base does not reload the base.
  - `generate()` and `generate_image()` must only be called from the worker thread.
  - Reference videos: `generate(ref_video_paths=)` passes them to `ReferenceToVideo` as `ref_videos` (their soundtracks as `ref_video_audios`). `_ref_video()` decodes the first `frame_count(duration)` frames at 24 fps and scales them down to the job's pixel area, plus the same stretch of the audio. The node itself would put every reference video on a 1344×768 canvas whatever the job's size, and the reference tokens join every attention call: ComfyUI's VSA keeps the whole packed prefix (text and references) exact for every query, unlike FastVideo, which trained OmniRef with each reference video as its own sparse region at keep 0.1. Measured on 2026-10-24 (FastH3 OmniRef, 4090): a 5 s 544p shot with a 5 s reference samples in ~100 s (~26 s without), 768p ~144 s, 15 s with a 15 s reference ~561 s; none ran out of memory. A 1080p reference at 544p took the same time as a 544p one. The motion, camera, timing and scene carry over closely when the prompt replaces a subject.
  - Guide audio: `generate(audio_path=, audio_start=)` loads the slice of the file that matches the shot (`_audio_clip()`, via ComfyUI's audio `load`) and chains `MiniMaxH3AddGuide(frame_idx=0, audio_vae=, audio=)` after ImageToVideo / ReferenceToVideo, so it works in every video mode. The anchored slice comes back nearly unchanged in the output audio.
  - Pictures: `generate_image()` runs MOSS-Image with the ComfyUI template settings (`IMAGE`: 25 steps, cfg 2.5, er_sde, simple, the template's negative prompt; ~1 MP sizes from `image_size()`). The MOSS UNET, text encoder (CLIPLoader type `moss_image`) and VAE load lazily on the first picture job and stay loaded next to the H3 models; DynamicVRAM moves weights as needed. The template's prompt expansion (TextGenerate) is left out: it took ~45 s and made results worse.
  - Music: `generate_music()` runs MiniMax Music 3 like the ComfyUI template (`MUSIC`): `MiniMaxMusic3TextEncode` (the text encoder autoregressively writes acoustic tokens; cfg_scale 1.7, top_k 50; its `seconds` output is the actual length, which can be shorter than `max_duration`), `ConditioningZeroOut` as negative, `EmptyMiniMaxMusic3LatentAudio`, KSampler 30 steps euler/simple cfg 1.7, `VAEDecodeAudioTiled` (1536/64). `_save_mp3()` writes VBR mp3 V0 with PyAV, because the system ffmpeg on the GPU box has no libmp3lame. int8 DiT and text encoder (CLIPLoader type `minimax`), loaded lazily and kept resident like MOSS. Stages: loading, composing, sampling, decoding, saving. Measured on the 4090: a 60 s song ~100 s (composing 68 s, sampling 28 s), 30 s ~60 s. The engine must run ComfyUI's per-node cleanup (`_after_node()`: `cleanup_prefetch_queues`, `reset_cast_buffers`, `vbars_reset_watermark_limits`) between music nodes and after the job: the AR text encoder records a per-thread CUDA malloc graph, and without the cleanup the second music job in the process fails with a device-side assert / CUBLAS error that poisons the CUDA context until restart.
  - Upscaling: `upscale_video()` runs SeedVR2 3B int8 like ComfyUI's `utility_seedvr2_3b_int8_upscale_video` template (`UPSCALE`): lanczos resize to `upscale_size()` (short side from `UPSCALE_TARGETS`), `SeedVR2Preprocess`, `VAEEncode`, KSampler 1 step euler/simple cfg 1 with `SeedVR2Conditioning`, `VAEDecode`, `SeedVR2PostProcessing` (color correction none). Unlike the template it splits the latent with `SeedVR2TemporalChunk` (auto, sized to free VRAM, overlap 2) and merges with `SeedVR2TemporalMerge`, so long or 1440p clips fit on 24 GB, and it uses the plain VAE nodes instead of the template's 512 px tiled ones: SeedVR2's VAE sizes its work from measured memory figures and runs whole frames when they fit, and the forced tiles nearly doubled the VAE time (a 10.8 s clip to 1080p: 510 s tiled, 272 s plain; the DiT is ~19 s of it). Audio and frame rate come from the source file. The models load lazily and stay resident.
  - FlashVSR: `flashvsr_video()` runs FlashVSR v1.1 (`FLASHVSR`: int8 ConvRot DiT, Tiny decoder, attention auto, which picks Triton block-sparse) through T8star's FlashVSR+ node (`custom_nodes/Comfyui-Flashvsr-Plus-T8`, commit `ac60d1e`; `_flashvsr_runtime()` imports its `flashvsr_plus` package and uses `ModelHandle` / `InferenceRequest`). It streams the source mp4 straight to the output mp4 (the node's default `Options`; source audio copied by its ffmpeg mux), with no ComfyUI VIDEO round trip; the canvas is padded to multiples of 128 and cropped back. The handle keeps the pipeline in CPU RAM between jobs. FlashVSR allocates with plain torch, outside ComfyUI's memory management, so `flashvsr_video()` first moves every ComfyUI model off the GPU (`unload_all_models`); without that, upscaling right after a video job ran out of memory with the H3 weights still resident. Measured: the same 10.8 s clip to 1080p in 87 s including the first load. Weights in `models/flashvsr_plus/` from `t8star/Flashvsr-Plus-Comfy`.
  - `POST /api/jobs/{id}/upscale` (form `upscaler` seedvr2 / flashvsr, `target`, optional `seed`) creates the job; the `source` column holds the source job id (the worker resolves its video file at run time) and `upscaler` the choice (NULL on old jobs means seedvr2).
- `server/h3_jobs.py`: sqlite job store with a thread lock. The `result` and `refs` columns hold JSON. New columns get an ALTER TABLE migration in `__init__`.
- `server/app.py`: aiohttp application factory and entry point (~65 lines). `server_settings.py` owns environment/path settings passed through `app["settings"]`; HTTP handlers live in `http_api/{system,jobs,submissions,frontend}.py`, form builders in `job_forms/`, upload decoding in `job_uploads.py`, JSON representation in `job_views.py`, and FIFO execution in `job_worker.py`. Tests call `make_app(settings, engine=stub, start_worker=False)` rather than monkey-patching global directories.
  - A worker thread loads the models and runs jobs one at a time in FIFO order.
  - Endpoints: `/api/health`, `/api/presets`, `GET/POST /api/jobs`, `/api/jobs/{id}`, `POST /api/jobs/{id}/cancel`, `POST /api/jobs/{id}/upscale`, `DELETE /api/jobs/{id}`, `POST /api/unload`. `/api/unload` (refused with 409 while a job runs or waits) runs `engine.unload()` on the worker thread through `Worker.call()`: it drops the base DiT, its clones and the lazy MOSS / music / SeedVR2 / FlashVSR models, unloads the rest from VRAM and empties the cache, so another program (e.g. faster-whisper) can use the GPU; the next job reloads what it needs and `/api/health` reports `unet: null` until then. Static files are under `/files/{videos,pictures,thumbs,uploads}`; every other path goes to the frontend.
  - `POST /api/jobs` takes a multipart form: `prompt`, `resolution` (544p / 768p), `lora` (optional; defaults to the recommended LoRA; the server checks that its base family and resolution match), `lora_strength` (0–2, default 1; stored in the `lora_strength` column and recorded in `result.models`; the engine caches clones per (LoRA, strength) and keeps only the latest non-1.0 strength), `sampler` (optional, one of `SAMPLERS` in `model_catalog.py`: euler / res_multistep / er_sde; empty or the model choice's own sampler stores NULL in the `sampler` column, and larryvrh, FastH3 and Pika (`fixed_sampling()`, set by `fixed` in `LORAS`) ignore it; the engine swaps only the KSampler, so no new model clone), `steps` (optional, `STEPS_RANGE` 1–30; the model choice's own count stores NULL in the `steps` column, and FastH3 ignores it; the engine rebuilds only the sigmas; API only, the form just shows the model choice's count), `duration` (2–15 s), `seed`, `aspect_ratio` (`image` follows the input picture's ratio), `image`, `last_image`, `ref_image` (up to 6, repeatable), `ref_video` (up to `MAX_REF_VIDEOS` 3, repeatable, at least 2 s; stored in the `ref_videos` JSON column, served as `ref_video_urls`; the prompt calls them `<Video k>` after the images, and their soundtracks `<Audio k>`), `audio` + `audio_start` (guide audio; stored in the `guide_audio` / `audio_start` columns, served as `guide_audio_url`). The job mode is one of t2v / i2v / fl2v / r2v; r2v (ref2va base) is chosen by reference images or videos or by a ref2va `lora`, so it also runs with zero references (the frontend then leaves out subject_definitions and retention_analysis). The form hides model groups with no choice for the mode (Reference shows FastH3 and Pika) and gives the user's picked group back when they switch to a mode that has it. A form with `kind=image` selects `image_model` (`moss` by default, `flux-klein-4b`, `qwen-image-21-turbo`), `prompt`, `aspect_ratio`, `seed`. Optional repeatable `ref_image` or single `image` inputs create an i2i edit (up to four inputs; MOSS supports generation only); otherwise mode is t2i. Qwen edits require `aspect_ratio=image`. The PNG name goes in `picture`. Image history additionally filters by `image_model`; NULL legacy choices map to MOSS. `kind=music` creates a t2m job (`prompt` = caption, `lyrics`, `duration` 10–300 s as the maximum length, `seed`); lyrics go in the `lyrics` column and the mp3 name in `audio`.
  - `/api/presets` returns `resolutions`, `groups`, `loras` (each with `group` and `fixed`, which hides the sampler picker), `default_loras`, `samplers`, `steps_range`, `image` (legacy MOSS defaults plus `choices` with per-model sizes, capabilities and models), `music` (length range and models) and `upscale` (targets and `upscalers` with their models). The job's `preset` column holds the resolution and the `lora` column the LoRA key; old combined ids such as `ref-544p` are migrated at startup by `backfill_lora(LEGACY_PRESETS)`.
  - LoRAs and jobs carry a `models` field (base, LoRA, sampler, shift) for the frontend to display. Finished jobs read the models they actually ran on from `result.models`, so later LoRA config changes do not relabel old jobs.
  - index.html is re-read on every request, so a frontend-only deploy needs no restart.
- `server/h3-server.service.in`: systemd unit template. `deploy.sh` replaces placeholders such as `@USER@` and `@DIR@` with values from `.env` before installing it; the unit activates ComfyUI's Python environment and then runs `app.py`.
- `web/src/generationModes.js` / `components/ModeNav.vue`: single registry for vertical navigation grouped by video, image, audio and 3D. History follows the selected family: `GET /api/jobs?kind=video|image|music|3d` filters both the rows and X-Total-Count (omitting kind still lists all jobs). Video includes all video modes and upscale. The UI resets pagination on family switches and ignores stale in-flight responses.
- `web/src/components/GenerateForm.vue`: lightweight family router with KeepAlive; delegates reuse and picture-to-3D/video actions. `forms/VideoForm.vue`, `PictureForm.vue`, `MusicForm.vue`, `MeshForm.vue` own their settings; video prompt fields and model settings are separate children. `composables/useGeneration.js` owns shared submission and per-family drafts (migrates `h3.form.v2`); `useVideoPrompt.js` owns prompt assembly/parsing. `FormFooter.vue` shares seed, submit and error UI.
- Native audio: `audio_catalog.py` pins the three speech families and Qwen3-ASR (Qwen TTS has three 1.7B Q8 variants; Qwen ASR adds its Q8 Forced Aligner and tiny Silero VAD dependency). `audio_runtime.py` owns a loopback CUDA audio.cpp v0.9.3 child with one resident model, lazy loading and no idle eviction. `pipelines/audio_cpp.py` uses native speech/transcription HTTP endpoints, with PCM conversion in `audio_media.py`; there are no ComfyUI inference nodes on this route. `job_forms/audio.py` validates speech/clone/design and ASR uploads; modes `tts`/`asr`, `audio_model`, `audio_options`, `input_media` columns. `transcript_exports.py` exports only real timestamps: Qwen aligned words and grouped cues. Retired model metadata is displayed from stored results, without keeping retired models configured. Runtime settings `H3_AUDIOCPP_*` are documented in `.env.example` and README. Prepare with `--only audio`; reusable downloader in `scripts/model_download.py`, safe runtime installer in `scripts/prepare_audio_runtime.py`. Keep weights/runtime/configs/logs out of Git.
- LLM: `llm_runtime.py` owns a loopback Strata child (`serve/server.py --engine strata --config $H3_STRATA_CONFIG --parallel $H3_STRATA_PARALLEL`, port `H3_STRATA_PORT`); `pipelines/llm.py` runs one `kind=llm` job = a JSONL batch of chat bodies with a thread pool (`concurrency`, default 16 > 8 slots so slots never idle), retries each request up to 3 times (transport error, `length`, invalid structured JSON) and writes `data/llm/<job>.jsonl` incrementally (`.part` until done). Per-request failures are recorded, not raised. `job_forms/llm.py` validates ids/messages; options in the `llm_options` column. `runtime_memory.prepare()` stops Strata before any non-LLM task (it fills the 24 GB card) and stops audio.cpp + offloads ComfyUI when entering it; consecutive LLM jobs keep it running. Strata lives outside this repo (`H3_STRATA_DIR` on the GPU box, built from source for driver 570 / CUDA 12.8).
- Cross-runtime VRAM: native audio runs in the same Studio FIFO worker as ComfyUI jobs. Entering audio.cpp offloads ComfyUI GPU weights; leaving audio unloads its native weights before ComfyUI allocation checks, stops the child if private caches still prevent headroom, and preserves same-model residency otherwise. Native cancellation kills only the owned Popen child and resets on the next request; never adopt or kill another process bound to the audio port.
- `server/runtime_memory.py`: worker-owned admission/residency policy called by all engine pipelines. Reuse warm weights for healthy repeat jobs; use native minimum inference headroom and pressure-based `free_memory`, fall back to full offload, and reject jobs if other GPU processes still leave too little headroom. Entering Pixal3D/FlashVSR offloads ComfyUI models for their external allocators. Image/video model changes target only the old patchers/clones. Worker OOM recovery runs after leaving the exception block so traceback tensors can be freed; no automatic retry. Failed recovery marks health error and stops the worker, preserving queued DB rows. Health `memory` is a worker-recorded snapshot. Keep the meshing-stage Pixal offload and FlashVSR upstream CPU offload; do not remove them just to maximize residency.
- `server/image_models.py`: standard-library image catalog, exact sampling defaults and six new weights with pinned SHA256 hashes. `pipelines/image_runtime.py` caches one image model family at a time; switching drops the old image family and unloads VRAM. `klein.py` mirrors the official 4-step distilled Flux2Scheduler/ReferenceLatent workflow; `qwen_image.py` uses native TextEncodeQwenImage21, auto/default KV cache and the official 8-step manual sigmas. Input images are about 1 MP; Qwen edits follow the first image canvas. `prepare_models.py --only klein qwen-image` downloads just the new weights; `--only image` includes MOSS too. Optional `--workers` and `--connections` (aria2c) speed downloads; the new groups verify existing files and downloads. Klein VAE is aliased locally to `flux2-vae-klein.safetensors` to preserve an existing VAE of the same upstream filename.
- `server/pipelines/pixal.py`: native single-image Pixal3D pipeline, lazy models in `H3Engine._pixal`, dropped by `unload()`. Model manifest `PIXAL_FILES` in `model_catalog.py`; `prepare_models.py --only pixal3d` prepares them. `kind=3d` → `i23d`, one image required, `mesh_options` records resolution, texture size and background removal, `model_3d` stores the GLB under `data/models3d/`. Uses native BiRefNet/MoGe/DINOv3, 12/20/12/12 euler steps, structure shift 5 and official CFG patches; defaults 1024 geometry / 2K texture, 100k triangles, PBR base/metallic/roughness maps. Always run the official solid RemeshMesh (768, fill 20, band 1, smooth 20) before decimation, and bake against the original decoded reference mesh; skipping remesh caused thousands of holes/overlapping shells. AO/normal-map baking is omitted. `components/ModelPreview.vue` lazily imports the local model-viewer bundle on click.
- `web/src/components/RefImages.vue`: reference image list, each image with a subject description. Image N is `<Subject N>` / `<Picture N>`. With `video` it is the reference video list: video k is `<Video k>` and `<Subject images + k>`.
- `web/src/components/ImageDrop.vue`: drag-and-drop upload for the first / last frame.
- `web/src/components/ActionStrip.vue` / `UpscaleMenu.vue`: single-row scrolling actions with wheel/touchpad/keyboard support; upscale options teleport out of the scroll container and close on scroll/Escape/outside click.
- `web/src/components/JobCard.vue`: job card with progress, video, picture or audio player (with lyrics), reuse button, Reference / Frame buttons on pictures and an Upscale menu (upscaler × targets above the video's size) on videos; the prompt is clamped to three lines with a Show more toggle.
- `doc/directing-workflow.md`: the agent workflow for directing any multi-shot production through the API. Confirm the brief, landscape/portrait, resolution (768p default), reference-to-video mode, spoken language, visual treatment and subtitle translation language first. Write the complete story, character/dialogue/narration/location bible and storyboard under `outputs/<title>/`; generate and freeze character and empty-location references with the current picture models. Generate 5–15 s FastH3 OmniRef segments using the embedded official prompt format, fixed voice descriptions (no external TTS), speech/action budgets and explicit continuity between segments; independent jobs may queue together without mandatory two-minute approval gates. Assemble the whole film, transcribe the final edit through the Qwen3-ASR API, review/correct actual speech, translate it into the requested language, and embed source and translation as two selectable soft subtitle tracks without burning text into the picture. Deliver the film, cover, publish notes and both SRTs. Follow it when asked to make a multi-shot video.
- `doc/novel-adaptation-workflow.md`: adapt a novel/novella one source chapter per independent video. First inspect existing chapter divisions, delivered videos, progress and in-flight jobs; continue from the earliest unfinished chapter without restarting completed work. Read the current chapter, consulting earlier/later passages only as needed; no full-book reading or season-plan prerequisite. Adapt and compress nonessential/redundant plot before storyboarding, then follow `directing-workflow.md` through the full chapter film and Qwen3-ASR bilingual soft subtitles. Keep a searchable shared character/location image library under `outputs/<novel-title>/`, reuse it across chapters, and register new character images for growth/age or clothing/accessory changes without overwriting prior versions. Principal/recurring roles need cards; one-off minor roles and extras may use prompt descriptions only. Record chapter status and the exact next action in `PROGRESS.md`. Follow it when asked to adapt a book.
- `doc/narrated-image-workflow.md`: the separate still-image route for illustrated channels and series (history, children's picture books, science and other topics). Plan the requested episode outlines, complete narration scripts and dense visual beats, lock the style, and generate all artwork through Studio's image API with `image_model=qwen-image-21-turbo` by default. Generate fixed character references first; defined characters use edit mode with repeatable `ref_image`, other images use generate mode. Generate narration through Studio's own `kind=speech` TTS API (e.g. Qwen3-TTS), measure actual audio, obtain real alignment via Studio ASR when needed, and apply Ken Burns locally. Use Studio's own APIs throughout; follow this guide for image sequences instead of H3 audiovisual generation.

## Deployment

```bash
./deploy.sh          # frontend + server (restarts the service)
./deploy.sh web      # frontend only; no restart, loaded weights are unaffected
./deploy.sh server   # server only (restarts the service)
./deploy.sh models   # download models on the GPU machine; extra arguments go to prepare_models.py
FORCE=1 ./deploy.sh server   # restart even while jobs are running or queued (they are lost)
```

- The frontend is built locally with `npm run build`; dist is copied with scp to `web_dist.new` and swapped in atomically.
- `deploy.sh` reads `.env` first; environment variables already set on the command line take precedence over `.env`. Each setting is documented in `.env.example`.
- The server code (`server/` and `comfy_launcher/run_h3.py`) is rsynced to `$H3_DEPLOY_DIR` (default: the remote user's `~/minimax-h3-studio`); then the systemd unit is rendered, installed and restarted, and `/api/health` is polled until the state is ready.
- URL: `http://<host of H3_DEPLOY_HOST>:<H3_PORT>`
- Data directory on the server: `$H3_DATA_DIR` (default `$H3_DEPLOY_DIR/data/`; put it on a large disk, since outputs grow by tens of GB), containing `jobs.db`, `videos/`, `pictures/`, `music/`, `thumbs/`, `uploads/`.
- Logs: `ssh $H3_DEPLOY_HOST journalctl -u h3-server -f`
- Environment variables read by the server process: `H3_COMFYUI` (required), `H3_DATA`, `H3_WEB_DIST`, `H3_HOST`/`H3_PORT`, `H3_COMFY_ARGS`.

## Local development

```bash
cd web && npm install && npm run dev   # vite reads the root .env and proxies /api and /files to H3_API (default: the deployed machine)
```

For comparison tests, stop the service first (`sudo systemctl stop h3-server`) to free the GPU, copy `comfy_launcher/` to the GPU machine, set `H3_COMFYUI` inside ComfyUI's Python environment, and run bench.sh:

```bash
./bench.sh <name> --jobs-json prompts_stylized.json --steps 4 --width 960 --height 544 \
  --shift-video 12 --lora <lora>.safetensors -- --enable-triton-backend --use-sage-attention
```

Results land in `out_<name>/` and can be rsynced to a local `outputs/` (git-ignored). Afterwards run `sudo systemctl start h3-server`, or simply rerun `./deploy.sh`.

## Browser QA cleanup

After viewport emulation for screenshots, always call CDP `Emulation.clearDeviceMetricsOverride` and restore emulated media in a `finally` block before leaving or releasing a tab. A fixed 1440×1000 emulated viewport outlives the test: with Chrome's debugger banner visible, it can exceed the real window height and make the form's bottom controls unreachable even at maximum scroll. Validate scrolling once with natural window dimensions and the debugger banner still showing, then release the tab to detach the debugger.
